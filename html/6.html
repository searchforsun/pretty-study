一、工具调用的本质与协议

术语解释

工具调用（Tool Calling）：让大模型能够调用外部函数或 API 来获取信息或执行操作的技术。模型本身不执行代码，只生成结构化的调用意图，由应用层解析并执行。

函数调用（Function Calling）：OpenAI 提出的标准工具调用格式，现已成为行业事实标准，Anthropic、Google、阿里、字节等主流厂商均已对齐。

JSON Schema：描述工具参数结构的标准格式，模型据此生成合法参数。

tool_choice：控制模型是否必须调用工具的策略参数（auto / required / none）。

🔤 英文名称速查

名称是什么 / 干什么
system / user / assistant / tool对话四类角色：系统指令、用户提问、模型回复、工具执行结果
tool_callsassistant 消息里的结构化字段：要调哪个函数、参数 JSON
tool_call_id一次工具调用的唯一 id；tool 消息必须带它才能和调用对应
JSON Schema描述函数名、参数类型与必填项；模型据此生成合法 arguments
tool_choiceauto 模型自定 / required 必须调工具 / none 禁止调工具
ReActReason→Act→Observe 循环；多步工具调用与推理框架
max_iterationsAgent 最多循环几轮，防止无限调工具
MCPModel Context Protocol，标准化接入外部工具/数据源，减少重复胶水代码
Guardrail输入/输出防护：拦截注入、过滤敏感信息、校验格式

核心原理

工具调用的本质是：模型生成符合特定格式的文本，由解析器解析并执行外部函数，然后将函数返回结果传回模型生成最终回答。

关键认知：大模型是「决策者 + 文案生成器」，不是「执行者」。所有副作用（查数据库、发邮件、改文件）必须在应用侧受控执行。

对话中的四种角色

角色 谁写入 内容
system 开发者 系统指令、工具列表、行为约束
user 用户 用户问题或指令
assistant 模型 自然语言回复，或 tool_calls 结构化调用
tool 应用层 工具执行结果（必须带 tool_call_id 对应关系）

函数调用完整工作流程

sequenceDiagram
    participant Dev as 开发者
    participant App as 应用层
    participant LLM as 大模型
    Dev->>App: 定义工具 JSON Schema
    App->>LLM: 注入 tools + 用户提问
    LLM->>App: tool_calls
    App->>App: 执行函数(权限校验)
    App->>LLM: tool 角色消息(结果)
    LLM->>App: 最终回答
    Note over App,LLM: 结果不足时可多轮 tool_calls
文本版流程（ASCII） 
① 开发者定义工具（name + description + parameters JSON Schema）
② 将工具列表注入 system prompt 或 tools 字段
③ 用户提问 → 模型判断是否需要工具
④ 模型输出 tool_calls（JSON：工具名 + 参数）
⑤ 应用层解析 JSON，执行对应函数（带权限校验）
⑥ 将 tool 角色消息（执行结果）追加到对话历史
⑦ 模型读取结果，生成最终自然语言回答
   └─ 若结果不足，可再次发起 tool_calls（多轮工具调用）

工具定义示例（JSON Schema）

{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定城市当前天气。仅当用户询问天气、穿衣建议时使用。",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "城市名，如：上海、北京"
        },
        "unit": {
          "type": "string",
          "enum": ["celsius", "fahrenheit"],
          "description": "温度单位，默认 celsius"
        }
      },
      "required": ["city"]
    }
  }
}

如何定义一个好的工具

要素 反例 ❌ 正例 ✅
名称 tool1、do_stuff get_weather、search_orders
描述 「查询信息」 「按订单号查询电商订单状态，返回物流与支付信息。用户需提供 order_id。」
参数 无 description 的 string 每个字段写明格式、示例、是否必填
边界 两个工具功能重叠 「何时用 A、何时用 B、何时都不用」写清楚

并行 vs 串行工具调用

  • 并行调用：多个工具互不依赖时，一次响应中输出多个 tool_calls，应用层并发执行（如同时查天气 + 查航班）
  • 串行调用：后一步依赖前一步结果（如先查用户 ID，再查订单列表）
  • 最佳实践：能在 description 里写「可与其他工具并行」的，尽量让模型一次发起多个调用，减少往返延迟

主流厂商工具调用对比

厂商 协议名称 特点
OpenAI Function Calling / Tools API 生态最成熟，支持 parallel tool calls
Anthropic Tool Use 与 OpenAI 结构类似，Claude 工具遵循度高
Google Function Declarations Gemini 原生支持，适合多模态场景
阿里 / 字节 兼容 OpenAI 格式 通义、豆包等国内模型可直接复用 OpenAI SDK
重要结论：工具调用的可靠性约 90% 取决于工具定义的质量；其余 10% 来自模型能力与错误处理。

应用价值

  • 让大模型获取实时信息（天气、新闻、库存、股价）
  • 让大模型与外部系统交互（数据库、CRM、工单系统）
  • 让大模型执行受控操作（发通知、创建任务、生成报表）
  • 将「只会说话」的模型变成「能做事」的应用入口

常见问题解释

Q：为什么模型总是调用错误的工具？

A：工具描述不清楚，或工具之间功能重叠。优化 description，明确「适用 / 不适用」场景，必要时减少工具数量。

Q：模型编造了工具返回结果怎么办？

A：模型在未真正执行工具时可能幻觉出结果。务必走完整流程：只有应用层执行函数后，才将 tool 消息写入历史；禁止模型自行「假装」已调用。

Q：需要几个工具才合适？

A：生产环境建议单 Agent 控制在 5–15 个工具；过多时按领域拆分子 Agent 或做工具路由。

二、Agent 本质与 ReAct 框架

术语解释

Agent（智能体）：能自主感知环境、制定计划、执行行动、根据反馈调整策略的循环系统。与「单次问答」或「单次工具调用」不同，Agent 允许多轮推理与行动。

ReAct：Reason + Act 框架，核心是「思考 → 行动 → 观察」循环，是目前最常用、最易调试的 Agent 模式。

Observation：工具或环境返回的反馈，驱动下一轮思考。

核心原理

Agent 的本质是：一个由大模型驱动的「规划—执行—反思」循环，在终止条件满足前反复调用工具。

什么时候需要 Agent？

场景 推荐方案 原因
固定流程、步骤已知 普通 Chain / 工作流 无需模型动态规划，更稳定、更便宜
单步查资料 + 回答 RAG 或单次工具调用 一步即可完成，不必上 Agent
步骤不确定、需试探 ReAct Agent 模型根据中间结果决定下一步
复杂任务需先拆计划 Plan-and-Execute 先规划再逐步执行，减少盲目调用

ReAct 框架完整工作流程

flowchart TB
    R1["思考 Reason"] --> A1["行动 Act"]
    A1 --> O1["观察 Observe"]
    O1 --> C1{{"足够回答?"}}
    C1 -->|否| R1
    C1 -->|是| ANS["回答 Answer"]
文本版流程（ASCII） 
思考(Reason)：我需要做什么来解决这个问题？
行动(Act)  ：调用工具(参数)
观察(Observe)：工具返回的结果
思考(Reason)：根据结果，下一步做什么？是否已足够回答？
行动(Act)  ：…（重复）
…直到满足终止条件…
回答(Answer)：汇总最终答案

ReAct 框架完整示例

用户问题：上海今天的天气怎么样？适合穿什么衣服？

思考：需要先查上海天气，再根据气温和天气状况推荐穿着。

行动：get_weather(city="上海")

观察：晴，25–30°C，南风 3 级，湿度 60%。

思考：气温较高、晴朗，无需雨具，适合轻薄透气衣物。

回答：上海今天晴，25–30°C，建议短袖、短裤或裙装，注意防晒。

多步推理示例（需多次工具调用）

用户问题：帮我查一下订单 ORD-8821 的状态，如果已发货就告诉我预计到达日期。

思考：先查订单状态，再根据状态决定是否查物流。

行动：get_order(order_id="ORD-8821")

观察：状态：已发货，物流单号 SF1234567890。

思考：已发货，需查物流 ETA。

行动：track_shipment(tracking_no="SF1234567890")

观察：预计 2026-06-14 18:00 送达。

回答：订单 ORD-8821 已发货，预计 6 月 14 日 18:00 前送达。

Agent 的三大核心组件

  1. 规划器（Planner）
    • 将复杂任务分解为子任务
    • 根据 Observation 动态调整计划
    • 决定何时停止循环、输出最终答案
  2. 工具执行器（Tool Executor）
    • 解析 tool_calls，映射到真实函数
    • 参数校验、超时、重试、权限控制
    • 将异常转为模型可理解的 Observation
  3. 记忆系统（Memory）
    • 短期记忆：当前会话的 messages 历史
    • 工作记忆：中间结论摘要（避免上下文爆炸）
    • 长期记忆：用户偏好、历史交互（通常走向量库或数据库）

Agent 循环的控制参数

参数 推荐值 说明
max_iterations 5–15 最大循环次数，防止无限循环
max_execution_time 30–120s 总超时，避免用户长时间等待
early_stopping 开启 模型输出最终答案格式时提前终止
return_intermediate_steps 调试时 true 返回每步思考与工具调用，便于排查

应用价值

  • 解决需要多步推理和多次工具调用的复杂任务
  • 构建客服、运维、数据分析等自主辅助系统
  • 在不确定路径的场景下，比硬编码工作流更灵活

常见问题解释

Q：什么时候用 Agent，什么时候不用？

A：步骤固定 → 用 Chain；单步查资料 → RAG/单次工具；步骤不确定、需多轮试探 → 用 Agent。过度使用 Agent 会增加成本、延迟和不稳定性。

Q：ReAct 和 Function Calling 是什么关系？

A：Function Calling 是「单次或多次工具调用」的协议；ReAct 是在此之上的「思考—行动—观察」编排模式。Agent = 编排 + 工具调用 + 终止条件。

三、Agent 架构模式与框架选型

常见 Agent 架构模式

模式 流程 适用场景 优缺点
ReAct 思考→行动→观察 循环 通用探索型任务 简单易懂；步数多时上下文膨胀
Plan-and-Execute 先出完整计划，再逐步执行 步骤多、结构清晰的任务 计划稳定；计划错误时难纠正
Reflexion 执行→评估→反思→重试 代码生成、需要自我纠错 成功率高；多轮反思成本高
Multi-Agent 多角色分工协作 研发、审核、翻译等多专长 能力边界清晰；协调复杂
LangGraph 状态机 显式节点 + 边 + 状态 生产级、需人工介入的流程 可控性强；开发量较大

MCP：工具接入的标准化方向

MCP（Model Context Protocol） 由 Anthropic 推动，旨在用统一协议连接「模型 ↔ 工具/数据源」，类似 USB 接口。Cursor、Claude Desktop 等已支持 MCP Server。

  • 工具提供方实现 MCP Server，暴露 Resources / Tools / Prompts
  • 客户端（IDE、Agent 应用）通过 MCP Client 发现并调用
  • 优势：一次接入、多处复用；减少每个项目重复写工具胶水代码

国内常用 Agent 框架对比

框架 特点 适用场景 学习曲线
LangChain 组件最全，文档丰富 快速原型、通用 Agent 中
LangGraph 有状态图、支持 Human-in-the-loop 生产级复杂流程 中高

Dify / Coze 低代码可视化编排 业务人员参与、快速上线 低
选型建议：学习原理用 LangChain ReAct；上生产优先 LangGraph 或 Dify（视团队技术栈）；Multi-Agent 仅在单 Agent 工具过多或角色边界明确时使用，避免过早复杂化。

应用价值

  • 根据任务复杂度选择 ReAct / Plan-and-Execute / 状态机
  • 用 MCP 减少工具接入重复劳动
  • 避免「一切皆 Agent」的过度设计

四、常见问题、安全与生产实践

Agent 六大常见问题与解决方案

问题 最可能的原因 最佳解决方案
无限循环 无终止条件或 Observation 无信息量 max_iterations + 明确停止指令；工具返回结构化错误
规划失败 任务过复杂或模型能力不足 任务分解、换更强模型、Plan-and-Execute
工具调用错误 描述不清、参数 schema 模糊 优化 description、Pydantic 校验、few-shot 示例
忘记之前步骤 上下文过长、关键信息被淹没 定期摘要中间结果；只保留最近 N 轮 tool 消息
成本/延迟过高 循环次数多、模型过大 小模型路由 + 大模型规划；缓存相同工具结果
结果不可复现 temperature 高、工具非确定性 Agent 用 temperature=0；记录完整 trace

提升 Agent 可靠性的 8 个技巧

  1. 用更强模型做规划（GPT-4o、Claude Sonnet、Qwen-Max 等）
  2. 工具 description 写清「何时用 / 何时不用」
  3. 应用层做参数校验，错误信息回传模型自我修正
  4. 要求模型在行动前先输出简短思考（CoT）
  5. 限制 max_iterations 和总超时
  6. 对关键操作加 Human-in-the-loop 确认
  7. 记录每步 trace（LangSmith、Langfuse、自建日志）
  8. 为工具调用做集成测试（固定输入 → 期望工具名与参数）

工具调用安全清单

  • 最小权限：每个工具只暴露必要 API，禁止模型直接执行任意 SQL / Shell
  • 参数白名单：枚举、正则校验，拒绝 eval、路径穿越等
  • Prompt 注入防护：用户输入与 system 指令隔离；工具结果当不可信数据处理
  • 敏感操作二次确认：删数据、转账、发邮件等需用户或审批流确认
  • 审计日志：谁、何时、调用了什么工具、参数与结果

成本与延迟优化

策略 效果
Router 分流简单问题 减少 50%+ 不必要的 Agent 调用
工具结果缓存（相同参数） 降低外部 API 费用与延迟
压缩 Observation（只传摘要） 减少 token 消耗
并行 tool_calls 缩短多工具场景的总耗时

应用价值

  • 快速排查 Agent 线上问题（循环、幻觉、工具误调）
  • 满足企业安全与合规要求
  • 在效果与成本之间做可量化的权衡

常见问题解释

Q：为什么 Agent 总是陷入无限循环？

A：模型认为任务未完成，或工具返回空/错误信息导致反复重试。设置 max_iterations，并在 system 中定义「满足 X 条件即输出 Final Answer」。

Q：如何调试 Agent？

A：开启 verbose / trace，逐步查看：用户输入 → 模型思考 → tool_calls → 工具返回 → 下一轮。重点检查工具是否被误选、参数是否解析错误。

📝 2 小时实战小练习

以下示例使用 OpenAI 兼容 API + 原生 Function Calling，再附 LangGraph 最小 Agent 写法（2024–2026 主流栈）。

练习 A：原生 Function Calling 循环

import json
from openai import OpenAI

client = OpenAI()  # 或 base_url 指向通义/DeepSeek 等兼容端点

tools = [{
    "type": "function",
    "function": {
        "name": "calculator",
        "description": "计算数学表达式，支持 + - * / 和括号",
        "parameters": {
            "type": "object",
            "properties": {
                "expression": {"type": "string", "description": "如 12345 * 67890"}
            },
            "required": ["expression"]
        }
    }
}]

def run_calculator(expression: str) -> str:
    allowed = set("0123456789+-*/(). ")
    if not all(c in allowed for c in expression):
        return "错误：表达式含非法字符"
    try:
        return str(eval(expression, {"__builtins__": {}}, {}))
    except Exception as e:
        return f"计算错误: {e}"

TOOL_MAP = {"calculator": lambda args: run_calculator(args["expression"])}

messages = [{"role": "user", "content": "计算 12345 * 67890 的结果"}]

for _ in range(5):  # max_iterations
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
        tools=tools,
        tool_choice="auto"
    )
    msg = resp.choices[0].message
    if not msg.tool_calls:
        print("最终回答:", msg.content)
        break
    messages.append(msg)
    for tc in msg.tool_calls:
        args = json.loads(tc.function.arguments)
        result = TOOL_MAP[tc.function.name](args)
        messages.append({
            "role": "tool",
            "tool_call_id": tc.id,
            "content": result
        })

点击查看答案
  1. 模型生成结构化调用意图，由应用层解析执行；模型不直接执行函数
  2. 应用层写入；必须带 tool_call_id 与 assistant 的 tool_calls 对应
  3. 思考(Reason) → 行动(Act) → 观察(Observe)
  4. 规划器、工具执行器、记忆系统
  5. 步骤不确定、需多轮工具 → Agent；固定流程 → Chain；单步检索 → RAG
  6. 工具定义（name、description、parameters）的质量
  7. max_iterations、总超时、明确终止条件、有信息量的 Observation
  8. 工具/数据源接入的标准化，避免重复胶水代码
  9. 最小权限、参数校验、敏感操作确认（另：审计日志、防 Prompt 注入）
  10. Plan-and-Execute 先出完整计划再逐步执行；ReAct 每步根据观察动态决定下一步
